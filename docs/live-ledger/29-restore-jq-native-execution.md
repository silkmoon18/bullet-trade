# API20：恢复JQ原生执行

日期：2026-09-09。范围：本地修正，不推送、不部署、不改变服务器交易状态。

## 原因和决定

原双账户方案（`4737357`）要求JQ沿用聚宽原生接口，QMT执行由服务器负责。`6071765`为了处理JQ未成交新增了分钟续单、持久化计划及全部卖完后再买的机制，超出了这个边界。

用户9月9日日志确认API19生效：158005连续九次未成交并被聚宽取消，第十次于09:39成交，三个新标的因此到09:39才买入。这是新机制造成的执行时点变化，不是当日重复成交。另在本地发现SELL阶段缺少逐标的完成记录，会在等待其他卖单时因涨价再次减仓；不再沿着这套非目标机制继续补功能，而是定向撤回。

## 切片与实现

1. **还原JQ执行**：`JoinQuantRuntime.execute_rebalance`恢复为`6071765^`的完整方法。非目标持仓原生清仓调用之后，按选股权重原顺序调用目标市值接口；保留原生市价类型及资金不足处理，不额外等待成交、不补单。原有决策时撤单行为保留。
2. **删除扩展机制**：删除`_jq_plan`、计划保存/恢复、分钟续行、SELL/BUY阶段判断和风控停止补买代码；删除策略`handle_data`及`.pyi`的`on_bar`。旧`g.bt_jq_plan`仅作为聚宽可能保留的惰性数据，任何执行路径都不读取或恢复它，不改写现有账户持仓。
3. **策略与版本边界**：保留选股数据时间、过滤、排序、精确权重及风控阈值；删除安装函数无用的运行时state返回值，以及误称已经成交完成的开盘结束日志。helper API升为20，防止旧策略调用已删除的分钟入口；配置schema仍为3、执行协议仍为2。AGENTS.md明确JQ原生/QMT服务器执行隔离，禁止在修复中再次静默扩展JQ语义。
4. **验证与导出**：用原生执行契约替换API19续单测试，验证卖出取消/挂单/部分买入/None返回不会创建补单计划；验证旧计划恢复不发单、双账户隔离及原风控调用不变。导出单文件helper和策略，名称/过滤修复保留。

## 未改动项与实际代价

- QMT的订单类型、原始参考价、服务器回调追单、先卖后买、对账及午夜过期规则不变。没有把JQ订单控制搬到服务器。
- JQ原生调用可能出现卖出未成交但继续尝试买入，资金不足时由平台裁剪或拒绝；本次不承诺本轮目标一定完成，不以“减少未成交”为由再次改变JQ行为。
- 无成交后的自动重试不再存在；只有下一次原有策略决策/风控调用才可能提交新的JQ委托。JQ与QMT的成交时间、数量和收益不要求相同。
- 159086/588370可卖为0导致QMT阻断的问题不在本轮修改范围，不能声称因此恢复QMT交易。
- 前一轮本地飞书阻断详情增强保留；尚未部署，不修改其交易判断。
