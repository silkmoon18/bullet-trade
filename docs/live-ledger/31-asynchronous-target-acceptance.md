# 目标接收与券商执行解耦

## 问题与决策

`strategy.submit_targets` 原来在 RPC 内等待券商下单及成交等待。原生提交卡住时，RPC 的超时取消会把已经落库的订单变为 `SUBMIT_UNKNOWN`。可卖不足的行情唤醒又绕过了正常执行条件，持续触发同一个对账异常。

本次只修改服务器，不修改 GoodETF 决策、价格、JQ 原生撮合或 helper API 20。

## 切片

1. 目标及 outbox 落库后立即返回接收结果；服务器拥有后台执行任务。返回值不是成交确认，后续状态使用 intent/snapshot 查询和回报获取。相同意图的后台提交合并。
2. StrategyLedger 下单传 `wait_timeout=0`，拿到柜台订单号即保存，不等成交。原生提交单独限时；超时仅表示结果未知，不撤单、不重发。关闭服务时保留未知结果。
3. 已阻断或正在执行时，行情不重复推进；券商回报仍可触发只读核对与恢复。相同阻断原因不重复发卡片；未知提交展示标的与本地委托引用，不再显示 `None`。
4. 回归测试、代码审查，确认无重复发单、无虚构成交、无 JQ 行为变化。

## Session

- 本轮：本地修复及测试，不部署、不处理现存未知委托。
- 仅查询不到委托不等于提交失败；必须按原订单号或完整 client_tag 精确恢复，不能按同标的历史买单猜测卖单结果。
- 后台化只隔离 RPC 生命周期，不保证券商接口永不卡顿，也不保证成交。

## 接口与运行说明

- `strategy.submit_targets` 仍先做账户、行情与目标校验。目标落库后即返回，`dispatched_orders` 为 `[]`；这不表示下单失败。`snapshot` 包含本次计划新增的冻结，是接收时快照而非成交回报。
- 委托/成交通过原有 `strategy.get_intent`、`strategy.get_snapshot` 与通知获取。客户端不要因为接收响应里没有柜台委托就换新幂等键重发。
- 30 秒是单次券商提交响应的等待上限，不是目标有效期或撤单时间。目标仍限当天、午夜处理过期；限价和追单规则不变。
- 后台任务归服务器所有；服务关闭会取消后台等待并记录不确定结果。原生 SDK 线程不一定同时停止，所以不能因此推断柜台没有下单。
- 重启后，对账 READY 且处于发单时段，恢复已持久化但未发出的目标。未知提交必须先获得原委托的有效证据，不能重新排队。
